# Chessling 수 해설·퀴즈 설계 문서

- 작성일: 2026-10-01
- 상태: 설계 확정, 구현 계획 작성 전
- 선행 스펙: `2026-09-30-chessling-design.md`, `2026-09-30-chessling-renewal-design.md`. 이 문서는 해설·퀴즈만 추가한다.
- 브랜치: `main`에서 새 기능 브랜치를 만들어 진행한다.

## 1. 목적과 범위

기보를 넘기거나 리뷰할 때 **수마다 한마디씩** 코멘트를 붙인다.
**명경기**에는 해설자가 쓴 것처럼 "어떤 의도로 이 수를 뒀는지"를 담은 질 높은 해설을 붙인다.
중요한 장면에서는 다음 수를 공개하기 전에 사용자가 직접 둬 보는 **퀴즈**를 제공한다.

세 부분으로 나뉜다.

| 부분 | 내용 |
|---|---|
| 1부 | 명경기 해설 데이터와 제작 흐름. 30판, 1,879수. |
| 2부 | 일반 대국(내 대국·대회) 코멘트 생성기. 엔진 리뷰 결과로 만든다. |
| 3부 | 퀴즈. 명경기는 직접 고른 장면, 일반 대국은 자동으로 고른 장면. |

### 품질 기준

- 사람이 쓴 것처럼 자연스러워야 한다.
  - 해요체를 쓴다.
  - "중요한 순간입니다" 같은 상투어, "~것입니다"체, 번역투를 쓰지 않는다.
  - 같은 문장을 반복하지 않는다.
- 사실이 정확해야 한다.
  - 해설에 나온 수는 그 포지션에서 실제로 둘 수 있는 수여야 한다.
  - 형세 표현은 엔진 평가와 방향이 맞아야 한다.
- 스포일러를 내지 않는다. 앞으로 나올 실제 기보 수를 이름(SAN)으로 언급하지 않는다. 대신 "퀸 희생을 준비한다"처럼 의도로 말한다.

### 범위 밖

- 서버, LLM API 호출. 모든 생성은 브라우저 안에서, 명경기 해설은 미리 작성해 번들에 넣는다.
- 기존 출판 해설(책, 잡지, 웹)을 옮기거나 다듬어 싣는 것. 해설은 엔진 분석과 널리 알려진 역사적 사실만 바탕으로 새로 쓴다.
- 오프닝 이름 데이터베이스(ECO).
- 다른 기기와 퀴즈 기록을 동기화하는 것.

## 2. 1부: 명경기 해설 데이터와 제작 흐름

### 2.1 데이터 형식

경기마다 파일 하나: `src/data/annotations/<slug>.json`. 그 경기를 열 때만 동적 `import`로 불러온다.

```ts
interface Annotations {
  slug: string
  version: 1
  /** plies[i]는 i번째 수(1부터)를 둔 직후에 보여 줄 해설. 0번(시작 포지션)은 경기 소개 한두 문장 */
  plies: AnnotatedPly[]
  scenes: QuizScene[] // 3부
}

interface AnnotatedPly {
  ply: number // 1..N, 0은 시작 포지션
  text: string // 1~2문장. 핵심 장면은 3~6문장
  key?: boolean // 핵심 장면(승부처). 판정 카드에 '핵심 장면' 표시
}
```

- 모든 수(0..N)에 항목이 있어야 한다.
- 판정 라벨은 해설 데이터에 넣지 않는다. 판정은 기존 리뷰가 계산한다.
- 명경기는 리뷰 전에도 해설을 보여 준다.

### 2.2 팩트 시트(제작용, 저장소에 올리지 않음)

`scripts/annotate/facts.ts`는 node에서 Stockfish(`npm run engine:smoke`와 같은 방식)로 각 경기의 모든 포지션을 분석한다.

- 분석 깊이는 22, MultiPV는 3이다.
- 결과는 `scripts/annotate/facts/<slug>.json`에 저장한다. 이 경로는 `.gitignore`에 넣는다.
- 각 수에 담는 항목:
  - 수 전후 FEN, 실제 수(SAN/UCI)
  - 전후 평가(cp/mate), 승률
  - 최선 수 3개와 각 평가, 1순위 수순(최대 8수)
  - 기물 손익
  - 2부 감지기가 찾은 전술·포지션 사실(포크, 핀, 공짜 기물 등)
  - 판정 라벨(`judgeMove`)
- 팩트 시트는 해설을 쓸 때만 참고하는 근거 자료다. 앱 번들에 들어가지 않는다.

### 2.3 자동 검증 (vitest, `src/data/annotations/annotations.test.ts`)

모든 해설 파일에 대해 아래를 확인한다.

1. **범위:** 0..N의 모든 수에 비어 있지 않은 `text`가 있다. 핵심 장면(`key`)은 경기당 2~10개다.
2. **수 표기 합법성:** 본문에서 SAN 모양의 토큰(`[KQRBN]?[a-h]?[1-8]?x?[a-h][1-8](=[QRBN])?[+#]?`과 `O-O(-O)?`)을 뽑는다. 각 토큰은 다음 중 하나에 해당해야 한다.
   - 이미 둔 수(1..ply)
   - 해당 수 직전 포지션의 합법 수(안 둔 대안)
   - 해당 수 직후 포지션의 합법 수
   - 본문에 `[[...]]`로 감싼 가정 수순 안의 수. 예: `[[9...cxd5 10. exd5]]`. 가정 수순은 해당 수 직전이나 직후 포지션에서 순서대로 둘 수 있어야 하고, 화면에서는 변화 수순 서체로 보여 준다.
3. **스포일러 금지:** 토큰이 실제 기보의 이후 수(ply+1..N)와 같은 SAN이면 실패한다. 단, 같은 토큰이 2번 규칙의 대안·가정 수순으로도 설명될 때는 예외다.
4. **형세 방향:** 본문에 "백이 이긴다/우세", "흑이 이긴다/우세", "균형" 류 표현이 있으면, 해당 수 직후의 엔진 평가 구간과 맞아야 한다. 이 항목은 팩트 시트가 있을 때만 검사하고 CI에서는 건너뛴다. 대신 제작 단계에서 반드시 돌린다.
5. **문체 금칙어:** "~것입니다", "중요한 순간", "놀라운", "~라고 할 수 있습니다" 등 목록으로 검사한다. 목록은 테스트 파일에 둔다.

### 2.4 제작 순서

1. **시범 2판.** 오페라 게임(`opera-game`, 33수)과 세기의 대국(`byrne-fischer-1956`, 82수)을 먼저 쓴다.
   - 사용자가 문체, 깊이, 퀴즈 장면을 확인하고 기준을 확정한다.
   - 확정한 기준은 `docs/superpowers/annotation-style.md`에 남긴다. 예시 문장과 금칙어를 담는다.
2. **나머지 28판.** 경기마다 아래를 거친다.
   1. 팩트 시트를 만든다.
   2. 해설과 장면을 쓴다.
   3. 자동 검증을 통과시킨다.
   4. 문체 검토자가 AI 티와 번역투를 점검한다.
   5. 사실 검토자가 팩트 시트와 대조한다.
3. **브라우저 확인.** 판마다 넘겨 보며 읽는다. 모바일에서는 판정 카드가 접히는지 함께 확인한다.

## 3. 2부: 일반 대국 코멘트 생성기

`src/engine/comment/`. React와 무관한 순수 함수로 만든다. 리뷰 결과에서 매번 다시 만들 수 있으므로 저장하지 않는다.

### 3.1 입력과 출력

```ts
interface CommentInput {
  plies: Ply[]
  positions: ReviewedPosition[] // 리뷰 결과(score, best, pv, second, legalMoves)
  labels: (MoveLabel | null)[]
  index: number // 코멘트할 수(1부터)
  seed: string // 게임 키. 문장 틀 고르기에 쓴다
}
interface MoveComment {
  text: string
  facts: FactKind[] // 테스트와 디버깅용
}
```

### 3.2 사실 찾기(감지기)

`chess.js`로 수 전후 포지션을 보고 아래 사실을 뽑는다. 감지기마다 파일 하나와 단위 테스트 하나를 둔다.

- **전술**
  - 잡기: 무엇이 무엇을 잡았는지
  - 되잡기
  - 체크
  - 메이트, 메이트 위협(엔진 수순)
  - 포크: 움직인 기물이 상대의 값어치 높은 기물이나 방어 없는 기물 2개 이상을 공격
  - 핀, 꼬치
  - 숨은 공격
  - 공짜로 놓인 기물: 공격받는데 방어가 없거나, 더 싼 기물에게 공격받음
  - 폰 승진, 통과 폰 전진
  - 백랭크 약점
- **놓친 수:** 판정이 실수·블런더·놓침이면, 최선 수(`positions[index-1].best`)를 뒀을 때 얻었을 것을 적는다. 기물 득, 메이트, 형세 차이 등이다.
- **조용한 수**
  - 마이너 기물 전개
  - 캐슬링
  - 중앙 폰 전진
  - 열린 줄이나 반열린 줄에 룩 올리기
  - 킹 앞 폰 이동(킹 안전 약화)
  - 더블 폰·고립 폰 생성
  - 같은 값의 교환
- **형세 흐름:** 승률 구간(승세 ≥ 90 / 우세 ≥ 65 / 균형 / 열세 / 패세)이 바뀌는 순간과 메이트 수를 적는다.

### 3.3 고르기

사실이 여럿이면 우선순위로 1~2개만 고른다.

- 실수·블런더·놓침: "왜 나쁜가"(물리는 기물, 놓친 수)를 먼저 말한다.
- 좋은 수·탁월한 수·최선 수: "무엇을 해냈나"를 먼저 말한다.
- 형세 구간이 바뀌었으면 마지막에 한 구절을 붙인다.

### 3.4 문장 만들기

- 사실 종류마다 사람이 쓴 문장 틀을 3~6개 둔다. 위치: `src/engine/comment/phrases.ko.ts`.
- 틀 고르기
  - `hash(seed + index)`로 정해서, 같은 수에는 늘 같은 문장이 나오게 한다.
  - 직전 3수에서 쓴 틀은 다시 쓰지 않는다.
- 조사(은/는, 이/가, 을/를, 으로/로)는 앞말의 받침에 맞춰 자동으로 붙인다. 기물 이름과 칸 이름("e5")이 대상이다. 칸 이름은 숫자를 읽는 음으로 받침을 판단한다(예: e5 → "오" → 받침 없음).
- 스포일러 규칙
  - 놓친 대안 수는 SAN으로 말해도 된다. 이미 지나간 수에 대한 얘기이기 때문이다.
  - 상대의 반격 수순 첫 수가 실제 다음 기보 수와 같으면, SAN 대신 칸·기물로만 설명한다(예: "d5가 비어요").

### 3.5 품질 확인

- 명경기 30판의 팩트 시트로 생성 결과를 경기별로 뽑는 스크립트(`scripts/annotate/preview-comments.ts`)를 둔다. 결과를 사람이 읽고, 문체 검토자에게도 샘플을 돌린다.
- 단위 테스트를 둔다.
  - 감지기: 포지션별 기대 사실.
  - 조사 처리.
  - 같은 입력이면 같은 출력인지(결정성).
  - 같은 틀을 연속으로 쓰지 않는지.

### 3.6 표시

- 일반 대국
  - 리뷰 전: 지금처럼 리뷰 안내를 보여 준다.
  - 리뷰 후: 판정 아래에 생성 코멘트를 붙인다.
- 명경기
  - 직접 쓴 해설을 우선한다.
  - 리뷰 전에도 해설이 보인다.
  - 리뷰 후에는 판정이 함께 붙는다.

## 4. 3부: 퀴즈

### 4.1 데이터: 장면

```ts
interface QuizScene {
  id: string
  startPly: number // 장면 시작 포지션(이 수까지 둔 상태)
  side: 'w' | 'b' // 사용자가 둘 쪽
  prompt: string // 예: "백이 공격을 준비할 차례예요. 어떻게 시작할까요?"
  steps: QuizStep[] // 사용자가 둘 수 1~4개. 사이의 상대 응수는 replyUci
  source: 'authored' | 'auto'
}
interface QuizStep {
  answerUci: string // 정답 수
  acceptUci?: string[] // 정답으로 인정할 다른 수(작성자 지정)
  replyUci?: string // 정답 뒤 상대 응수(마지막 단계는 없음)
  hint?: string // 한 줄 힌트
  refutations?: { uci: string; text: string }[] // 자주 틀릴 수에 대한 반박
}
```

### 4.2 장면 고르기

**명경기:** 작성자가 해설 파일의 `scenes`에 직접 넣는다.
- 결정타 몇 수 전의 조용한 준비 수가 핵심이면, 그 준비 수부터 시작한다.
- 한 방이 핵심이면, 그 수 바로 전에서 시작한다.
- 한 판에 2~5개를 둔다.

**일반 대국(자동, `src/quiz/selectScenes.ts`):**

1. **승부처 찾기.** 판정이 `blunder | mistake | miss | great | brilliant`인 수를 모은다.
2. **빌드업 거슬러 오르기.** 승부처 수 c에서 같은 편의 이전 수(c−2, c−4, …)를 차례로 본다.
   - 실제로 둔 수가 엔진 최선 수와 같고, 외길이었으면 시작점을 그 수로 당긴다.
   - 외길 기준: 최선 수의 승률이 2순위 수보다 `QUIZ_ONLY_MOVE_GAP`(기본 10)%p 이상 높다.
   - 위 조건이 깨지는 수에서 멈춘다.
3. **단계 만들기.**
   - 시작점부터 c 전까지: 실제 기보 수가 정답이다.
   - c가 실수류면: c의 정답은 엔진 최선 수다. 그 뒤는 엔진 1순위 수순을 따른다.
   - c가 좋은 수류면: c의 정답은 실제 수다. 그 뒤도 실제 기보를 따른다.
   - 사용자 쪽 수는 최대 4개다.
4. **외길 구간이 없을 때**(천천히 나빠진 포지션 실수 등): c 바로 전에서 시작하는 한 수짜리 장면으로 만든다.
5. **편과 개수.**
   - 사용자 아이디로 불러온 대국: 사용자 쪽 장면만 만든다.
   - 그 밖의 대국: 양쪽 모두에서 만든다.
   - 형세 변화가 큰 순서로 최대 5개.
   - 장면끼리 겹치면 큰 쪽만 남긴다.

### 4.3 채점 (`src/quiz/grade.ts`)

- **정답:** 사용자의 수가 `answerUci` 또는 `acceptUci`이면 맞음이다.
  - 600ms 뒤 `replyUci`를 자동으로 둔다(모션 줄이기 설정이면 즉시).
  - 그다음 단계로 넘어간다.
- **그 밖의 수:** 분석 엔진으로 짧게 평가한다(movetime 약 300ms).
  - **정답만큼 좋으면**(승률 차 ≤ 3%p): "좋은 수예요. 실제로는 다른 수를 뒀어요."를 보여 주고 장면을 맞음으로 마친다. 이후 흐름이 달라지기 때문이다.
  - **나쁘면:** 기물이 되돌아간다. 반박을 보여 주고 다시 둘 수 있게 한다.
    - 반박은 `refutations`에 있으면 그것을 쓴다.
    - 없으면 엔진 응수를 2부 감지기로 문장화한다(예: "Qxd5는 Bxd5로 퀸을 잃어요").
- **결과:** 장면이 끝나면 "3수 중 2수 맞혔어요"를 보여 준다. 첫 시도에 맞힌 단계만 센다.

### 4.4 화면

- **시작**
  - 장면 시작 포지션에 오면 보드 오른쪽 위에 퍼즐 아이콘 버튼(오버레이, 44px)이 뜬다. 이름은 "퀴즈: 이 장면 직접 두기"다.
  - 전체 기보에서도 장면이 있는 수에 작은 퍼즐 표시가 붙는다.
- **퀴즈 중**
  - 판정 카드 자리가 퀴즈 카드로 바뀐다.
    - 질문
    - 단계 진행 표시(●●○)
    - 버튼: [힌트] [정답 보기] [그만두기]
  - 보드는 사용자 쪽 기물만 움직일 수 있다.
  - 평가 바, 엔진 라인, 화살표, 힌트 토글은 숨긴다.
  - 수 이동(조작 막대, 스와이프, 키보드)은 막는다.
  - [힌트]는 1단계로, 움직일 기물 칸을 표시하고 `hint` 문구가 있으면 함께 보여 준다.
  - [정답 보기]는 정답 수를 화살표로 보여 준 뒤 둔다.
- **끝나면:** [이어서 보기]를 누르면 해설 모드로 돌아가 승부처 수의 판정과 해설을 보여 준다.
- **접근성**
  - "수 입력(예: Nf3)" 칸으로 키보드·스크린리더 사용자도 풀 수 있다.
  - 맞음·틀림·결과는 `aria-live="polite"`로 알린다.
- **모션**
  - 맞으면 칸이 잠깐 빛나고, 틀리면 짧게 흔들린다.
  - `prefers-reduced-motion`이면 색 변화로만 알린다.

### 4.5 저장

- IndexedDB(Dexie) 새 테이블 `quizResults`.
  - 키: `[gameKey, sceneId]`
  - 값: `{ solvedSteps, totalSteps, attempts, completedAt }`
- 다시 열면 푼 장면에 ✓가 붙는다.
- 리뷰 요약에 "퀴즈 3/5"를 보여 준다.
- 자동 장면의 `sceneId`는 `auto-<startPly>-<side>`다. 리뷰 기준이 바뀌어 장면이 달라지면 기존 결과는 무시한다.

## 5. 판정 카드 변경

- 판정 아래에 코멘트 문단을 둔다.
- 2줄을 넘으면 접고 [더 보기] 버튼(`aria-expanded`)을 둔다.
- 핵심 장면이면 카드 위에 '핵심 장면' 배지를 단다.
- 스크린리더 알림(`aria-live`)은 지금처럼 판정만 알리고, 코멘트는 자동으로 읽지 않는다. 사용자가 카드로 이동해 읽는다.

## 6. 테스트

- **단위**
  - 감지기
  - 조사 처리
  - 문장 결정성과 반복 방지
  - 해설 파일 검증(2.3)
  - 장면 자동 선정: 빌드업, 최대 4수, 외길 기준, 대체 규칙
  - 채점: 정답, 대안, 오답, 반박
  - 퀴즈 중 잠금
- **컴포넌트**
  - 판정 카드 접기·펼치기
  - 퀴즈 카드 흐름
  - 수 입력 칸
- **E2E**
  - 오페라 게임에서 장면 하나를 끝까지 풀고, 새로고침 뒤 ✓를 확인한다.
  - 내 대국(모의 데이터)을 리뷰한 뒤 코멘트가 보이는지 확인한다.

## 7. 구현 순서(계획 작성 시 세분화)

1. 해설 데이터 형식, 불러오기, 판정 카드 표시. 우선 빈 해설로 시작한다.
2. 감지기와 2부 생성기. 단위 테스트와 미리보기 스크립트를 함께 만든다.
3. 팩트 시트 스크립트, 해설 검증 테스트.
4. 시범 2판 해설과 장면 작성 → **사용자 확인**.
5. 퀴즈: 장면 데이터·자동 선정·채점·화면·저장.
6. 나머지 28판 해설과 장면. 경기별 검증·검토를 거친다.
7. E2E, 전체 브라우저 확인.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 해설 분량(1,879수)이 많아 품질이 들쭉날쭉함 | 시범 2판으로 기준을 확정하고, 경기마다 자동 검증, 문체 검토, 사실 검토를 거친다. |
| 엔진 근거와 다른 서술(환각) | 팩트 시트 대조 검토를 하고, 수 표기 합법성 검사를 자동으로 돌린다. |
| 생성 코멘트가 기계적으로 들림 | 틀마다 여러 문장을 두고 반복을 막는다. 미리보기 스크립트로 사람이 읽고 문체 검토를 받는다. |
| 퀴즈 중 평가 바·화살표로 정답이 샘 | 퀴즈 모드에서 숨기고, 테스트로 확인한다. |
| 번들 증가 | 해설 파일은 경기를 열 때만 불러온다. 경기당 수십 KB다. |
